## Причина и исправление

В `../sd_live_j4_on_r2/uart_tx_timeout_analysis.json` сохранён реальный
отвергнутый ответ:39байт полного payload, а вместо его CRC уже `55aa0309`,
заголовок следующего ответа. Ожидаемый CRC этого payload — `f6e31d40`.
Nucleo сообщил `HAL_TIMEOUT=3` отправки. Блокирующий `HAL_UART_Transmit`
с общим лимитом5мс может вернуться до записи четырёх CRC-байтов, если
процессор задержан; последующий ответ тогда начинает новый кадр.
Настоящая ST HAL-функция с макетом периферии воспроизводит39-байтный
обрыв при введённой паузе main. Конкретная длительность/источник задержки
CPU в прежнем физическом событии не измерялись.

USART1 TX теперь использует свободный DMA1 channel1 / DMAMUX request25,
normal byte→byte, MINC, high priority. DMA2 channel1 остаётся SD,
DMA2 channels2/3 остаются MCSDK USART2 RX/TX. RX USART1 не переделывался.
Четыре буфера хранят собственные полные43-байтные кадры. При переполнении
отклоняется целый новый кадр, активный не перезаписывается. Следующий кадр
запускается только по USART TC после последнего стоп-бита; одного DMA TC
для завершения недостаточно. Ранний UART TC при CNDTR>0 не продвигает очередь.
OFF-подтверждение для пассивных страниц публикуется только после реального TC.

5-мс TX-контроль сохранён: задержка по-прежнему приводит к штатному STOP и
защёлке. Но timeout не отключает DMA, не меняет оставшиеся байты или буфер:
текущий кадр завершается вместе с CRC. Аппаратная ошибка DMA сразу снимает
MOE и запрещает перезапуск/подтверждение незавершённого кадра. CLEAR запрещён,
пока TX занят или имеет аппаратную ошибку. CRC32C, frame deadline15мс,
command watchdog300мс, бюджет восстановления2/1000мс, replay/sequence,
BKIN/температурные/шинные защиты и скалярное управление не ослаблены.

Промежуточная r1/1811/1810 сохранена отдельно и больше не используется.
На ней физическая проверка нашла один ложный TX-timeout при целых ответах:
время читалось до маскирования USART IRQ; TC мог начать следующий кадр
на новом миллисекундном отсчёте, после чего unsigned now-started давал
переполнение. В r2 часы читаются после маскирования писателя started_ms.
Тест явно воспроизводит TC непосредственно перед lock; отрицательный
контроль с прежним порядком чтения падает. Сохранены r1/status/registers:
timeouts1, completed2352, head=tail, DMA errors0, CRC ответов0. Это нельзя
выдавать за успешную окончательную r1-проверку или за порчу проводов.

## Следующий прогон

`tools/run_uart_tx_dma_to_50.py` подготовлен для точной пары1813/1812:
5→10→15→20→25→30→35→40→45→50Гц, минимум2с на каждой достигнутой ступени,
один START, общий host STOP100с, прежний operator watchdog3с,
STOP при нарушении состояния/защите/ошибке связи, повторов пуска нет.
После STOP ожидается9с для полного7,2-секундного D1/D2/D3 цикла;
сохраняются API-снимок и сырые320байт UART-reject при наличии.
18host-проверок готовности и14проверок единственного known-UV acknowledge PASS.

Если после снятия питания J1 осталась только известная низкая шина4,
подготовка может один раз CLEAR после её восстановления≥250В/soft-start,
при SDHIGH и пустом захвате. DP/BKIN, UART/CRC, занятую запись и действующую
защиту этот путь не принимает. Это не отключение защиты и не автоповтор
после аварии во время работы. Состояние/ACK сохраняются отдельно до START.

Стенд на момент принятия: обе платыUSBнаПК, J4=15Вon, J1off,
двигатель подключён/остановлен, Saleae отключён. Следующий физический шаг
запрошен пользователю: обе платы на повербанк, USBПК снять, при закрытом
стенде J1 через штатный soft-start;15В можно оставить. Пуск/RESET не нажимать.
Подтверждения этого переноса/включения ещё нет. До него моторный сценарий
не запускать. Ни50Гц, ни прежняя аппаратная IPM-защита около20Гц этим
idle-тестом не квалифицированы.
