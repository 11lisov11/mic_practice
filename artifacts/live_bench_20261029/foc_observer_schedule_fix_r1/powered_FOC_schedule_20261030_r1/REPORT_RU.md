# FOC3011/3012: ранний останов сценария, 30.10.2026

Пять секунд не пройдены. Ровно один CLEAR восстановил защиты, затем один START.
ШИМ выключен, STOP подтверждён. Записаны 39525 кадров АЦП и 2470 шагов
наблюдателя: около 2.470080с ШИМ по периоду таймера; сеанс Uno2516мс.
Это не независимое измерение длительности и не подтверждение физического вращения.

Нативный FOC в этом интервале не сообщил MA_STALE/MA_CURRENT/ошибку АЦП:
algorithm_fault0, first_faultNone, MCSDK masks0/0. Максимум observer wall
685,065мкс, CPUuppermax205,024мкс, maxqueue306,894мкс, resultagemax863,629мкс;
это раздельные максимумы, их нельзя складывать или выдавать за максимум
возраста оценки на каждом TIM1 IRQ. Fastmax4755<5312тактов.
Пороги1,35А/2048/2мс/RCM1мс/ADC187,5мкс не изменены.

## Почему прогон остановился

В журнале HMI зафиксирован OPERATOR_HEARTBEAT_LOST age=5.83s с STOP и ESTOP.
Скрипт не отправлял периодические POST /api/operator-heartbeat. ARM/START
и ожидание подтверждения расходовали часть heartbeat-окна ещё до включения ШИМ.
Итоговый first=ESTOP на Nucleo — полученная команда; это не MA_STALE.

Одновременно клиентский скрипт отказал по profile(): эта функция проверки
перед стартом ошибочно повторялась в RUN. При1893мс ШИМ веб вернул
zero_ready0, поскольку summary токов имела возраст2187мс, detail2888мс,
quality2438мс. HMI по умолчанию обнуляет этот вывод после истечения срока
телеметрии. Свежего отрицательного zero-флага в этой точке не получено.
В cm_core успешный zero_ready не сбрасывается во время RUN; реальный быстрый
контур проверяет sample.zero и sample.valid на каждом кадре. После остановки
токовые пакеты вернулись, прежние offsets/zero blocks сохранены.
Точный источник отсутствия токовых пакетов в RUN ещё не выделен: нельзя
называть доказанной причиной ни UART, ни snapshot, ни очередь передачи.

## Что исправлено и проверено без новых пусков

Только сценарий на ПК: heartbeat0,5с с подтверждением перед ARM, остановкой
при сбое и завершением после STOP; свежий автоноль по-прежнему обязателен
перед START. RUN отдельно проверяет свежие состояния нативного контура.
Просроченная производная индикация автонуля больше не считается новым
отрицательным измерением. Свежий zero_ready0 по-прежнему отвергается.
Ошибки SD/Break, UART, профиля, ADC, тока и возраста оценки не разрешаются.
Прошивки/HMI на платах не менялись. Счётчики и пороги защит не сбрасывались.

Тест на записанном статусе воспроизвёл прежний ложный отказ. Проверены
периодичность/завершение heartbeat и отказ при его потере, CRC/профиль/SD/
BIE/связь. Настоящий нативный C сохранил5 отказов: zero lost, invalidADC,
ADC age187,5мкс, estimate age2мс и raw current1,35А. Файл теста:
verification/host_supervision_fix_r1/report.json.

Токовая запись АЦП1024Б и CPU/IRQ42слова получены, исходный SD62мкс
сохранён byte-exact. Проверены SHA-2561594 старых файлов.
UART ORE/CRC/sequence/transport0; RPCcumulative12 не вырос.

Новое CLEAR/START не отправлялось. Силовое/15В и подключения по последнему
подтверждению пользователя не менялись, обе платы на повербанках.
Для нового сырого захвата нужна новая эпоха: peak capture сохраняет первый
пуск до reset; повтор без подготовки вернёт старый blob. Повтор пока
не разрешён; нельзя выдавать этот прогон за полные5сек FOC.
