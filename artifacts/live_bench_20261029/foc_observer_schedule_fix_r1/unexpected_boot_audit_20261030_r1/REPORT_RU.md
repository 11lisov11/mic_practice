# Проверка после ответа «Питание не прерывал»

Ответ пользователя принят: намеренного отключения питания между проверками не было. Отдельно проверены журналы Uno и код установленного пакета; прошивки не изменялись.

## Установлено

- Nucleo действительно повторно инициализировалась: свежий CRC-пакет D6 показывает уменьшение HAL tick с 164446 до 92544 мс, выбор алгоритма вернулся с FOC на V/f, появились восемь новых блоков автонуля вместо прежних трёх. Сейчас tick продолжает расти; это не застывшая копия старого статуса.
- Новый автоноль не готов: блоки 3 и 6 превысили предел оценки неопределённости среднего по V1 (2,071 и 2,002 отсчёта при пределе 2). Последняя серия имеет два стабильных блока вместо трёх; восемь попыток исчерпаны. Это не доказательство неисправного АЦП или инвертора.
- UART в сохранённом свежем статусе без ошибок, ШИМ выключен, состояние SAFE, контроллер показывает около 321 В. START/CLEAR/ARM/RESET не отправлялись.
- Linux Uno загрузился 30.10 в 12:50:09 UTC, boot ID 200d0429-13f5-4560-9dbf-25666845944e. Предыдущий журнал заканчивается обычной cron-записью в 12:50:01, без последовательности штатного shutdown. Запрос по ключевым словам причины сброса в журнале ядра не дал результатов. Отсутствие записи shutdown не определяет причину: питание, аппаратный reset и аварийный перезапуск этим не различаются.
- Нельзя по этому журналу утверждать, что Uno и Nucleo сбросились одновременно. Время записи файла последнего успешного статуса Nucleo — уже после времени начала новой загрузки Linux; сам файл не является синхронизированным регистратором момента сброса.

## Аудит кода и предел вывода

В main.c HAL_Init и mic_current_init вызываются при входе в main; повторного вызова в основном цикле нет. В установленном MCSDK существует программный путь SW_RESET → HAL_NVIC_SystemReset в mcp.c; найденный обработчик сам по себе не доказывает получение такой команды. Нет оснований объявлять все программные причины исключёнными. HAL-модули IWDG/WWDG в конфигурации не включены, но этого недостаточно для вывода об аппаратных option bytes.

Текущая телеметрия не содержит сохранённой при старте причины RCC reset. Поэтому различить сброс по питанию, NRST и программный сброс по этим захватам нельзя. Следующая целевая доработка — раннее сохранение и выдача причины reset и идентификатора загрузки, с проверкой на ПК до любой записи. До этого повторные reset и пуски не дадут отсутствующую причину прошедшего события.
