Исправления

Наблюдатель вызывается перед poll и между живыми диагностическими пакетами.
RX обрабатывается не более43байт за проход, затем управление возвращается
основному циклу. Обычный ответ управления и токовые данные остаются живыми.
Большие неизменяемые SD/ADC/noise/identification-буферы передаются после OFF;
сами ADC-выборки и захват продолжают работать. Это не удаление записей.

Поздний результат наблюдателя не публикуется после уже защёлкнутого IRQ-сбоя
или выключения MOE. Исходная метка результата остаётся временем реального
окна. Её не подменяют текущим временем ради прохождения проверки свежести.
Математика ma_observe/ma_control, параметры двигателя, токовые пределы,
геометрия/дедлайны АЦП, SD/BKIN, watchdog и автостоп5сек не менялись.
NVIC-приоритеты прежние; новых масок IRQ/PRIMASK/BASEPRI нет.

Разделение времени

Девять возвращающихся обработчиков в таблице векторов снабжены scope-метками.
IPSR/RETTOBASE отличают реальное корневое IRQ от вложенного или обычного
вызова C-функции. Интервал корневого обработчика включает вложенные один раз.
При раннем return выполняется GCC cleanup. Thread mode читает счётчики через
ограниченный seqlock, не останавливая прерывания.

На каждое наблюдение доступны wall, IRQ body и CPU upper=wall−IRQ body,
число корневых IRQ, задержка готового окна, возраст входа/результата.
Это осмысленные границы, а НЕ точное выделение каждой машинной инструкции:
вход/выход исключения, края профайлера и IRQ вне охваченного тела остаются
в CPU upper. Поэтому IRQ body — нижняя граница задержек, CPU upper — верхняя
оценка времени расчёта с этими накладными расходами. Максимумы отдельных
показателей могут относиться к разным вызовам; складывать максимумы нельзя.

Та же схема добавлена к прежней64-случайной OFF-проверке. Её результаты имеют
явную метку OFF_synthetic_CPU_probe и не выдаются за работу двигателя.
Первый аппаратный этап после установки — низкая шина/MOE0, не новый пуск.
Исходный OFF-гейт85000тактов и гейт ядра4000тактов сохранены; полный fast
по-прежнему проверяет5312тактов, ADC возраст3/16000сек, оценку2мс.

Первый отказ сохраняется атомарно до дальнейшей диагностики: причина,
код, DWT-время, метки ADC/оценки/bin, начало наблюдения, последний завершённый
CPU/IRQ-интервал, последовательность отсчёта, его valid/zero и признак
незавершённого наблюдения в момент отказа. Следующий отказ снимок не затирает.
ТелеметрияE8 имеет4страницы с CRC/проверкой peer/freshness. При смене режима
OFF/runtime или появлении первого fault сборка страниц начинается заново.
HMI отдаёт именованные поля foc_runtime и понятную причину первого MA_STALE;
на простой панели название алгоритма теперь берётся из nativeподтверждения.

Проверки наПК

- Точный native C: допуск расчётного профиля,5Гц/5сек, автостоп/переполнение,
  пять разных причин stale, неизменность первого снимка, CRC/peer/page/freshness.
- Вложенные IRQ и переполнение DWT/IRQсчётчиков без двойного учёта; ограничение
  попыток seqlock при искусственно нечётной последовательности.
- Настоящий TSK_HighFrequencyTask: V/f сохраняет угол/регулятор, FOC/adaptive
  пропускают чужой угол, ошибка всё так же выключает PWM.
- Настоящая порцияRX43байта и abort; при RUN объёмная диагностика отложена,
  контроль/токи остаются, при OFF сохранённые страницы снова передаются.
- Старый C воспроизводит MA_STALE на построенном расписании с реальными
  сохранёнными токовыми значениями и измеренным wall148155тактов; новый C
  проходит тот же сценарий с исходным2мс лимитом. Задержка foreground50000тактов
  и IRQ-расписание синтетические, не извлечены из старого аппаратного захвата.
  Это воспроизведение механизма starvation, не доказательство конкретной ветки
  прошлого запуска и не пятисекундная аппаратная квалификация.
- Обе сборки/Uno loader, Python/JS, правильные compile units/профиль в ELF,
  все девять возвращающихся реальных векторов IRQ, RAM/неизменность приоритетов.

Модельное исследование не повторялось: ядро управления/наблюдателя побайтно
прежнее. Хеш связывает прежние4/4центральных и54/60сценариев чувствительности
с текущим C-ядром; эти результаты не объявляются аппаратной проверкой.
769прежних файлов/захватов проверены SHA256. Ничего из них не удалено.

Артефакты и следующий шаг

Релизные хеши и installed=false находятся в manifest.json. Отчёты проверок:
verification/selftest.json, path_tests.json, latency_replay_r2/report.json,
elf_identity.json; полный перечень сохранённого — preserved_captures_sha256.json.

Для установки нужно J1OFF, независимый мультиметр ниже20В, обе платы USBПК.
15В, двигатель и проводку можно оставить. Установщик install_foc_runtime_fix.py
сверяет предшественника и шину, сохраняет SRAM/калибровку, пишет образы с чтением
обратно. verify_foc_runtime_idle.py проверит64OFFслучая и новые CPU/IRQграницы.
Ни один из этих инструментов не делает START или CLEAR. Без такой проверки
новый силовой пуск не планируется.

Основания метода: [ST PM0214,§4.4.3 RETTOBASE](https://www.st.com/resource/en/programming_manual/pm0214-stm32-cortexm4-mcus-and-mpus-programming-manual-stmicroelectronics.pdf#page=226).
Лишний вызов проверен по локальным исходникам MCSDK acim_vf_control.c:131
и mc_tasks.c:TSK_HighFrequencyTask, а не по предположению о помехах.
