# Разбор FOC1503/1504 и кандидат1601/1602

## Обновление:1601/1602 установлены, OFF CPU пройден

По отдельной команде пользователя при J1OFF, подтверждённых мультиметром
<20В, USBобеих плат и оставленных15В выполнена одна запись каждой MCU.
Оба образа проверены чтением обратно. Nucleo дополнительно прочитана
независимо:112936B, SHA256
`df78597cbcb2d2bbc7527401cda81cc55ec84b855085e4a90dc8ec60f353b0f0`.
Перед записью сохранены прежняя flash1504, RAM32КБ и резервная копия HMI.
Калибровка до/после совпала:
`a89603c26f3dfa6287c304134121028db6ebdb9adeda4b58d99040530ffeea17`.

Первый preflight остановился **до любой прошивки** из-за исторического
soft CRC-counter1. В8свежих ответах он оставался1 при bad_count0,
аппаратных UART flags0 и возрастающем good_count; доказательства сохранены
в programming_preflight_UART_r1. Исключение только для OFF-программирования
именно этого сохранённого счётчика не является исключением моторных START
проверок. CLEAR не выполнялся. Затем hardware_install_r2 выполнил запись.

Штатная проверка64случая×8повторов завершилась успешно:
**fast max3618 тактов ≤4000**, запас382такта; observer max18752≤85000,
meter_errors0, observer_steps64. Два пассивных RAM-снимка подтвердили один
и тот же результат; повторного RESET для выбора результата не было.
MOE0/BKE1/BIE1, running0, PA6HIGH, рекордер observer пуст.

Связь свежая:8ответов, hardware UART flags0, CRC/sequence counters0,
bad_count1 неизменен. Сохранился LINK_TIMEOUT7 после программирования,
и UNDER_VOLT mask4 при выключенном J1; они не очищались. Автоноль готов.

Доказательства: installation_acceptance.json, hardware_install_r1/report.json

исходные readback/RAM/статусы рядом с ними. Это успешная OFF CPU-проверка,
**не доказательство исправления NIS или доставки захвата при новом силовом пуске**.
Ниже сохранено описание офлайн-подготовки до этой установки.

## Исходный этап подготовки наПК

Работа выполнена **на ПК по сохранённой записи**, без обращения к платам,
пусков, CLEAR, RESET и перепрошивки. Подготовлены Uno2026111601 /
Nucleo2026111602, но **не установлены**. Старые исходники и failed-отчёты
не заменены; 3296 прежних файлов проверены по SHA256.

## Что доказано про потерю достоверности

В сохранённом прогоне FOC отработал5000мс. Возраст результата не превысил
771,524мкс при пределе2мс; запись не содержит MA_STALE или ошибки измерителя.
Причина первого отказа достоверности скорости — **OD_NIS**, шаг501:

| Величина | Значение |
|---|---:|
| Ошибка предсказания тока α | +0,010470 А |
| Ошибка предсказания тока β | −0,131268 А |
| Дисперсия инновации α / β | 0,000440893 / 0,000445147 А² |
| Вклад α / β в NIS | 0,248621 / 38,709181 |
| Общий NIS | 38,957802 |
| Граница достоверности | NIS <25 |
| Поток | 0,274007 Вб, выше неизменной границы0,125 |

Вклад β — **99,36%** NIS. Это пересчитано из самих ошибок и дисперсий,
а не из текста ошибки интерфейса. Метки endpoint ADC и входного окна
в первом снимке совпадают; подмены endpoint более новым foreground-отсчётом
в этой записи нет. За весь observer record: valid2484/invalid2511 из4995.
Наблюдатель предсказывает ток с ошибкой, превышающей заложенную неопределённость.

**Физическая причина этой ошибки ещё не определена.** Запись содержит12
редких состояний с шагом455 вычислений плюс первый отказ, а не непрерывную
последовательность входных токов/напряжений и ковариаций. По ней нельзя честно
восстановить5000 шагов EKF, выбрать моторные параметры, знак реальной скорости
или доказать, что виноваты только помехи АЦП. Напряжение в записи — модель
по CCR/dead-time, не измеренные напряжения двигателя; независимой скорости нет.
Поэтому R/Q, параметры двигателя, знак скорости, NIS25 и аварийные NIS50×20
**не изменялись**. Устранение потери достоверности пока не заявляется.

## Почему не дошёл сырой АЦП и что исправлено

В старом main.c отправка bulk выполнялась только при ответе на команду,
примерно раз в50мс. Порядок был фиксированным: repeat/boot/**observer**/
Break/**ADC**/noise/identification. Observer допускает следующую страницу
уже через20мс и бесконечно повторяет62 страницы. При head−tail=1 он добавляет
свою страницу, после чего ADC видит head−tail>1 и возвращается без отправки.
Ситуация может повторяться постоянно, без queue_full и без bad-пакетов.

Это воспроизведено с реальными функциями отправки observer/ADC из релиза
и моделируемой UART115200: старая версия за8с отправила observer15/ADC0
страниц, новая — observer397/ADC79; оба новых приёмника собрали полные записи.
Это проверка дефекта планирования, **не побитовое воспроизведение времени
UART аппаратного прогона**: временная трасса очереди в нём не записана.
Замороженное RMS-окно и отсутствие новых rejected frames дополнительно
согласуются с проблемой доставки, но RAM peak.frozen на том прогоне не читалась.

Исправление: bulk обслуживается в foreground после обработки RX/команд,
независимо от их50мс cadence; семь источников получают очередь по кругу,
поворот происходит только после реальной постановки пакета. За один вызов
ставится максимум один bulk-пакет, два места остаются для ответов управления.
При MOE/command_enabled или неподтверждённом safe-OFF передача bulk запрещена.
Обработчики UART/DMA, их watchdog, CRC, свежесть peer и первенство управления
не менялись. Ни один новый bulk-пакет не передаётся во время RUN.

Также исправлена отдельная ошибка хостового сборщика: он больше не берёт
декодер старого релиза с другой длиной observer record. Новый runner связывает
декодер с точным server.py своего пакета. Сохранённый observer1832B с CRC
успешно разбирается этим путём, без подмены прежнего failed-report.

## Как получим данные для разбора NIS

Добавлен диагностический запрос сырого АЦП **при первом отказе по NIS после
ранее достоверного состояния**. Foreground только выставляет однобайтовый
запрос; запись меняет исключительно существующий ADC IRQ. В кольце остаются
предыдущие реальные отсчёты и6 последующих; новые синтетические токи не создаются.
Исходная геометрия окна, допуски, принятие токов для обратной связи/RMS и
защита1,35А не менялись. Запись включает и невалидные кадры с явными flags,
чтобы исключить подмену реального выброса отбрасыванием.

Причина PC_OBSERVER=8 отличается от исходного порога626ADC counts; интерфейс
показывает её явно. Если первый пик уже сохранён, новый запрос его не стирает.
Если первый отказ был по другой причине, он также остаётся первым; этот пакет
не обещает перезаписывать кольцо для каждого последующего NIS.
Диагностика не меняет NIS, состояния EKF, решения о достоверности или защиты.

## Проверки на ПК

- Фиксированное старое расписание воспроизводит отсутствие страниц АЦП;
  новый арбитр доставляет observer и ADC в шести проверенных сочетаниях
  cadence/phase. В модели оба полных блока доходят примерно за1,3с/3,6с,
  все control replies сохранены, переполнений нет. Это не аппаратные замеры.
- Сырой1024B capture проходит реальные peak_core, приёмник Uno и HMI decoder;
  CRC, причина NIS,6 post-samples, укороченный STOP, старые пороги, запрет
  перезаписи frozen record и повреждённые данные проверены.
- Реальная функция native ma_observer_record проверена: прогрев не запрашивает
  захват, первое NIS-ухудшение запрашивает ровно один раз, NIS/state не меняются.
- Уравнения регулятора/EKF и временные тела fast/OFF-проверки совпадают
  с1503/1504. ARM scope не содержит новых вызовов в этих быстрых функциях.
- Семь сценариев независимой модели дают побитно те же итоговые траектории:
  nominal, Rs+20%, Rr+20%, Lm−5%, ADC±1/±16counts и задержка2,1мс. В последнем
  сценарии прежний MA_STALE останавливает привод. Сценарий ADC±16 даёт
  частые отказы достоверности, но не доказывает именно такую причину на стенде.
- Обе сборки успешны; Nucleo без предупреждений/ошибок, Uno LLEXT pass.
  RAM31408B из32768B, незарезервировано1360B. Максимум вложенного стека
  на железе заново не измерен.

Пределы **4000 тактов, 2мс, 1,35А, 2048** и остальные защиты сохранены.
Новый CPU-замер на MCU не выполнен, OFF_CPU_qualified=false. Предыдущие
3615 тактов относятся к установленной1504 и не переносятся на1602 как замер.
Перед будущим силовым тестом потребуются отдельная установка/readback и
OFF-квалификация. Сейчас новых пусков и физического переключения не требуется.
