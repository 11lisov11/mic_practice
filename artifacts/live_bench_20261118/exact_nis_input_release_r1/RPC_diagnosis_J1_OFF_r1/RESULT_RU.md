# RPC восстановлена в текущем сеансе; 180 секунд / 153 GET без новых ошибок

Пользователь подтвердил выключение только J1; 15 В и повербанки оставлены включёнными. Сбросов MCU/Nucleo, прошивок, START, ARM и CLEAR в этой диагностике не было. Авторизация на один CLEAR и один FOC5Гц/5000мс пока не израсходована; после нового подтверждения J1ON всё равно необходима свежая проверка защит.

## Фактические проверки

1. При входе GET через HMI снова давал503, Linux/SSH были доступны. Службы и подключения сохранены. Ошибка печати значка systemctl в Windows CP1251 затронула только вывод терминала; полный services_and_connections.log сохранён UTF-8.
2. Временный пользовательский экземпляр того же штатного arduino-routerv0.5.3 напрямую работал с UART и прошёл62GET за60с. Он завершён; порт основного router возвращён в finally с подтверждением true. Никакого прокси/подмены телеметрии/сбросов не было. Отличия опыта: новый процесс, verbose и отсутствие monitor-клиентов — по одному этому опыту первопричину установить нельзя.
3. На возвращённом основном router связь держалась42GET/48,094с, затем GET503; первая длинная проверка завершилась неуспешно через55,094с. Исходный failed-report сохранён.
4. На основном router обнаружен подключённый клиент Serial Monitor, хотя USB gadget затем подтверждён как not attached. Вызов Linux API mon/reset закрыл только monitor-сокеты (не MCU). Сразу после этого GET ещё не восстановился. Потом выполнен один close/open внутреннегоUART с той же паузой0,5с; подтверждено, что monitor-клиентов перед этим уже нет.
5. После этого основной HMI прошёл **153 свежих GET / 180,062с** без новых RPC/UART ошибок и перезапусков. RPC response/send timeouts=**254/0** неизменны во всём окне; старые ошибки не обнулены. SAFE/PWM0/run_id0/HVarm0; прогресс кадров/счётчика времени подтверждён, автоноль готов, OFFfast3804/4000, NIS/ADC-буферы свободны по телеметрии. Предел2мс/1,35А/2048 и все защиты неизменны.

Неиспользуемый monitor-клиент закрыт в текущем сеансе; постоянных изменений службы или исходников на платах не устанавливалось. Комбинация удаления monitor-сокета и восстановления UART проверена на180с, но это не отдельное доказательство причинности monitor, отсутствия гонки в другом компоненте или постоянного устранения проблемы после любой новой загрузки. Повторной провокации сбоя не выполняли.

Источник для проверки семантики Linux API: [Arduino monitor-api.go v0.5.3](https://github.com/arduino/arduino-router/blob/v0.5.3/monitorapi/monitor-api.go). mon/reset закрывает monitor TCP connections; это отличается от reset MCU. Исходник сохранён в upstream/. Накопленный Linux UART icount_overrun из отдельного снимка без измерения дельты не выдаётся за новую причину сбоя. Дополнительное ioctl-чтение при эксклюзивно открытом порте вернуло EBUSY; режим/права порта не менялись.

## Сохранённое состояние двигателя

Первый SD63,8мкс сохранён побайтно, SHA2562fb01b20ea604350f26a50c6a41372b19e258eb98951845826ee67dee5f2c6c5. SD сейчас HIGH, но BIEfalse и MCSDKcurrent/occurred4/4 остаются; CLEAR не делался. Это восстановленная связь, а не готовность к START. Старые8056файлов, свидетельства установки и прежнего CLEAR проверены по SHA без изменений.

Пользователь сообщил J1OFF; при этом свежая телеметрия показывает примерно320–321В на шине. Не утверждаем, что шина разряжена, и не подменяем это показанием мультиметра. Для описанных GET/сокетных проверок USB/проводку не подключали и перемонтаж не требовался.

После свежего подтверждения J1ON через soft-start можно продолжить уже разрешённый один CLEAR и затем один прогон, только если восстановятся все защиты. Следующая папка прогона FOC_5Hz_r2 (предыдущий FOC_5Hz_r1_RPC_preflight не перезаписывать). При новом отказе связи/защиты команду не повторять.
