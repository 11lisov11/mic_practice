# Модуль определения параметров асинхронного двигателя

## Что реализовано

Модуль `motor_identification` оценивает `Rs`, `Rr`, общую индуктивность
рассеяния `Lsigma`, взаимную индуктивность `Lm`, момент инерции `J`, коэффициент
вязкого трения `B` и дополнительный постоянный момент нагрузки `Tload`.

Расчёт выполняется только офлайн. CLI и HTTP API не содержат команд запуска,
не обращаются к `/api/cmd` и не могут включить ШИМ. До оптимизации обязательно
выполняется SVD/rank-gate для семи оцениваемых величин. После оптимизации
результат проверяется на отдельном наборе физических прогонов, который не может
иметь общие `run_id` с набором подгонки.

Раздельно оценивать `Lls` и `Llr` по имеющимся сигналам нельзя: исследование
показало потерю ранга. Поэтому в контракте используется только
`Lsigma = (Lls + Llr) / 2`.

## Почему `/api/status` недостаточно

Обычная телеметрия UNO Q/PC HMI содержит агрегированные токи и обновляется
намного медленнее электрических переходных процессов двигателя. Она пригодна
для защит, индикации и контроля опыта, но не для достоверной оценки `Rs`, `Rr`
и `Lm`. Модуль намеренно отклоняет редкие или неравномерные записи.

Для аппаратной идентификации STM32 должен записать синхронные отсчёты:

- время `t_s`;
- приложенные `v_alpha_v`, `v_beta_v` либо три фазных напряжения;
- токи `i_alpha_a`, `i_beta_a` либо три фазных тока;
- механическую скорость `omega_rad_s` или `omega_rpm`;
- идентификаторы калибровок токов, напряжения и скорости;
- точный хеш прошивки и источник тактирования ADC.
- идентификатор неизменной механической нагрузки и температуру двигателя для каждого прогона.

Для `standstill` и `free_run` период отсчёта должен быть не более `2 мс`, для
`coast` не более `20 мс`; jitter периода не более `5%`. Каждая серия начинается
после снятия возбуждения и размагничивания.
Все динамические fit/validation-прогоны должны иметь один `load_condition_id`,
а разброс температуры двигателя между аппаратными сериями не должен превышать
`5 °C`, иначе постоянные сопротивления и nuisance-момент относятся к разным
физическим условиям.

## Формат записи

Шаблон манифеста: `docs/motor_identification_capture.example.json`.
Шаблон начального приближения: `docs/motor_identification_prior.example.json`.
Поле `load_torque_scale_nm` задаёт характерный момент нагрузки конкретного
двигателя; оптимизатор использует диапазон примерно `±2` этого значения. Для
другой мощности нельзя оставлять масштаб от демонстрационного двигателя.

CSV может иметь один из двух наборов заголовков:

```text
t_s,v_alpha_v,v_beta_v,i_alpha_a,i_beta_a,omega_rad_s
```

или

```text
t_s,v_a_v,v_b_v,v_c_v,i_a_a,i_b_a,i_c_a,omega_rpm
```

Во втором случае преобразование Кларка и перевод об/мин в рад/с выполняются при
импорте. Имена колонок фиксируют единицы измерения и не допускают неявного
масштабирования.

## Команды

Проверка формата без расчёта параметров:

```powershell
py -3 -u tools\motor_parameter_identification.py validate `
  --input C:\capture_bundle
```

Идентификация и независимая проверка:

```powershell
py -3 -u tools\motor_parameter_identification.py identify `
  --input C:\capture_bundle `
  --prior C:\capture_bundle\prior.json `
  --output C:\capture_bundle\result.json
```

Синтетическая проверка программного контура, не являющаяся стендовым опытом:

```powershell
py -3 -u tools\motor_parameter_identification.py generate-synthetic `
  --output-dir tools\_research_exports\motor_identification_demo
py -3 -u tools\motor_parameter_identification.py identify `
  --input tools\_research_exports\motor_identification_demo `
  --prior tools\_research_exports\motor_identification_demo\prior.json `
  --output tools\_research_exports\motor_identification_demo\result.json
```

Локальный API анализа:

```powershell
py -3 -u tools\motor_parameter_api.py --host 127.0.0.1 --port 18110
```

API предоставляет только `GET /api/health`, `POST /api/validate` и
`POST /api/identify`. Полный `capture` и `prior` передаются JSON-объектами.

Строгий мост к будущему FOC-проекту:

```powershell
py -3 -u tools\mcsdk_motor_model_bridge.py render `
  --identification <hardware-result.json> `
  --profile docs\mcsdk_acim_motor_profile.iek_air56b2_catalog_operator_confirmed_vf_candidate.json `
  --output <motor-model-bundle.json>
```

Мост требует совпадение `motor_id` и числа пар полюсов, конечные SI-значения,
полный acceptance-gate и аппаратное происхождение. Флаг
`--allow-synthetic-dry-run` создаёт только `simulation_only`-артефакт и никогда
не разрешает генерацию FOC-прошивки или высоковольтный запуск.

## Условия принятия результата

Результат получает `accepted=true` только одновременно при выполнении условий:

- контракт и происхождение данных валидны;
- rank-gate до и после подгонки имеет ранг `7/7` и допустимое число обусловленности;
- оптимизатор сошёлся в достаточном числе независимых стартов и не упёрся в границы;
- максимальная относительная полуширина приближённого 95%-интервала не превышает заданный предел;
- остатки fit и независимого validation не превышают заданные пороги;
- измеренный и рассчитанный токи не превышают предел из prior.

Файл результата содержит хеши capture/prior, оценки, nuisance-параметр, метрики,
приближённые доверительные интервалы и явные blockers. Синтетический PASS не
помечается как аппаратная проверка. Блок `estimated_params` совместим с
существующим загрузчиком MIC AI; при этом `Ls=Lr=Lm+Lsigma`. Блок
`estimated_params_si` сохраняет явные единицы в именах полей.

Текущие 95%-интервалы являются локальной Fisher-аппроксимацией. Их фактическое
покрытие на нелинейной модели и при model mismatch ещё не откалибровано; поэтому
они пригодны для fail-closed фильтра ширины, но не для заявления о подтверждённом
95%-покрытии. Следующий статистический этап — отдельный MC-UQ coverage-аудит.

## Мост к MCSDK

Артефакт `mic_ai.motor_model_bundle.v1` явно фиксирует конвенцию
`Lsigma=Lls=Llr`, `LMS=Lm/1.5`, `LM=1.5*LMS`, а также производные `Ls`, `Lr`,
`tau_s`, `tau_r` и `sigma`. Сам bundle не разрешает HV: даже аппаратный кандидат
требует отдельной регенерации staging-проекта, проверки runtime-констант и стенда.

## Что ещё требуется от железа

Программный контур закончен и проверяется автоматически. Аппаратная
идентификация пока не подтверждена: существующая прошивка не выгружает
синхронный высокочастотный trace. Следующий отдельный этап — DMA trace recorder
на Nucleo G431 с низковольтным, ограниченным по току профилем возбуждения. До
прохождения safety/readiness gate автоматический запуск этого профиля запрещён.
